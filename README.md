# Local View B3D / B3D Publisher

Локальный Publisher для моделей БАЗИС 24. Цель production-маршрута — получить уже сформированную БАЗИС геометрию модели, без собственного восстановления пазов, спилов, отверстий и других обработок, и упаковать её в один автономный HTML для передачи заказчику.

## Production-маршрут

```text
B3D-Publisher.exe
  → официальный БАЗИС-Просмотр 3D (ViewerX.exe / Viewer24.exe)
  → загрузка исходного B3D
  → штатное сохранение текущей 3D-модели во временный VRML/WRL
  → чтение IndexedFaceSet / координат / нормалей / UV / материалов / текстур
  → компактный бинарный payload внутри HTML
  → один <имя модели>_просмотр.html
  → удаление временного WRL
```

Это не реконструкция геометрии B3D. Publisher не строит панели заново по контурам и операциям обработки и не выполняет CSG над содержимым B3D. Источником полигональной геометрии является штатный БАЗИС-Просмотр 3D, который сам открывает B3D и сохраняет загруженную модель.

Официальное руководство БАЗИС-Просмотр 3D прямо указывает, что утилита входит в комплект БАЗИС-Мебельщик, открывает модели системы БАЗИС (`b3d`) и умеет сохранять модели VRML (`wrl`). Команда «Сохранить» предназначена для сохранения текущего документа в другую папку или в другом формате.

Временный WRL — внутренний транспорт между установленным у автора модели БАЗИС 24 и Publisher. Заказчик его не получает; после сборки HTML временная папка удаляется.

## Что в production запрещено

В production не используются:

- собственный B3D → mesh реконструктор;
- `parser/b3d_parser.py` и `geometry/final_geometry.py` для формирования финальной геометрии;
- CSG/Manifold для восстановления обработок;
- OBJ, 3DS и DAE как производственный маршрут;
- облачный WebViewer;
- сетевые зависимости итогового HTML;
- обход лицензирования или ограничений БАЗИС.

Исследовательские файлы старых направлений могут оставаться в репозитории, но CI проверяет, что они не входят в сборку `B3D-Publisher.exe`.

## Почему выбран Viewer3D

Viewer3D — штатная часть установленной системы БАЗИС и предназначен именно для просмотра трехмерных моделей и их сохранения в различных форматах. Это даёт принципиально важную границу ответственности:

- БАЗИС формирует окончательную отображаемую геометрию;
- Publisher только принимает уже сформированные полигоны и упаковывает их для WebGL;
- Publisher не пытается интерпретировать внутренние технологические операции B3D.

Диагностический режим `--probe-b3d-handler` оставлен как дополнительное исследование Windows-ассоциаций B3D, но он больше не является блокером production-маршрута.

## Итоговый HTML

Заказчик получает только:

```text
<имя модели>_просмотр.html
```

HTML полностью автономен: без CDN, внешнего JavaScript, сервера, облака или интернета.

В payload встраиваются:

- позиции вершин;
- нормали;
- UV-координаты;
- индексы треугольников;
- цвет материала;
- текстуры, если Viewer3D экспортировал доступный файл текстуры;
- характерные физические рёбра для режима отображения рёбер.

Viewer поддерживает светлый фон, orbit-вращение, панорамирование и масштабирование, характерные рёбра, прозрачность, GPU picking, выделение, кнопку «Снять выделение» и `Esc` для снятия выделения.

## Windows EXE и gate

GitHub Actions собирает `B3D-Publisher.exe` как self-contained single-file Windows executable. Gate проверяет, что production-сборка содержит только маршрут:

```text
Viewer3DExporter → VrmlParser → OfflineHtmlPublisher
```

и блокирует попадание в production старого B3D-реконструктора, OBJ/3DS/DAE, облачного WebViewer и внешних зависимостей HTML.

## Проверка

```bash
python -m unittest discover -s tests -v
```

Windows workflow дополнительно компилирует `B3D-Publisher.exe`, вычисляет SHA-256 и сохраняет его как artifact для проверки на машине с БАЗИС 24.
