# Local View B3D / B3D Publisher

Локальный Publisher для файлов БАЗИС B3D. Production-маршрут читает данные модели **непосредственно из B3D**, строит итоговую твердотельную геометрию по сохранённым в файле контурам и операциям обработки и создаёт один автономный HTML для заказчика.

Текущая production-ветка: **direct B3D**.

## Production-маршрут

```text
B3D-Publisher.exe
  → BZ85 / B3D parser
  → Document / Model
  → панели: Contour + Thickness + Trans
  → обработки: Cut.Contour + Cut.Trajectory
  → sweep machining tool
  → manifold boolean difference
  → world/quaternion transforms
  → final triangle mesh
  → один <имя модели>_просмотр.html
```

Никакого промежуточного экспорта модели нет. Publisher не запускает БАЗИС, Просмотр 3D или облачный WebViewer.

В production **не используются**:

- BAZIS Script API;
- Viewer3D;
- VRML/WRL;
- OBJ, 3DS или DAE;
- WebViewer cloud;
- сетевые зависимости итогового HTML;
- обход лицензирования или ограничений БАЗИС.

## Что доказано на эталонном B3D

Эталон: `samples/Стол_3100х750х1300.b3d`.

Автоматические regression-тесты подтверждают:

- сигнатуру контейнера `BZ85`;
- чтение текущей ветки `Document → Model`;
- 37 панелей `Type 4002`;
- мировые координаты и quaternion-трансформации;
- итоговые границы модели примерно `3100 × 750 × 1300 мм`;
- 36 операций обработки;
- операции `typ=1`, `typ=4`, `typ=7`;
- построение всех 37 финальных solid без geometry errors;
- создание автономного HTML непосредственно из B3D.

Ключевой результат исследования: B3D хранит не только параметры операций, но и **геометрический профиль инструмента (`Cut.Contour`) и траекторию (`Cut.Trajectory`)**. Поэтому обработку можно применять единым геометрическим алгоритмом: профиль проводится по траектории и полученный объём вычитается из панели. Для четверти, спила 45° и скругления R2 не нужны отдельные рисованные «заплатки».

## Геометрический движок

Production-код:

```text
parser/b3d_parser.py
geometry/final_geometry.py
app/direct_publisher.py
```

`geometry/final_geometry.py`:

1. строит базовый замкнутый solid из внешнего контура панели и толщины;
2. вычитает внутренние контуры как отверстия;
3. декодирует профиль и траекторию каждой обработки;
4. определяет внутреннюю сторону панели относительно траектории;
5. строит swept tool для прямых и дуговых траекторий;
6. выполняет manifold boolean difference;
7. применяет иерархические мировые трансформации;
8. выдаёт финальную треугольную сетку для viewer.

## Проводник Windows и миниатюра B3D

Исследование этого направления тоже закрыто. В эталонном B3D обнаружено встроенное растровое preview: PNG находится в самом контейнере отдельно от основного zlib-потока `Model`. Поэтому миниатюра Проводника не означает, что Windows самостоятельно интерпретирует мебельную 3D-геометрию B3D; Проводнику достаточно встроенного preview.

## Итоговый HTML

Заказчик получает только:

```text
<имя модели>_просмотр.html
```

HTML полностью автономен: без CDN, внешнего JavaScript, сервера или интернета.

Viewer поддерживает:

- светлый фон без сетки;
- спокойное orbit-вращение без авто-анимации;
- панорамирование и масштабирование;
- реальные характерные рёбра с подавлением копланарных диагоналей триангуляции;
- отдельный режим прозрачности;
- GPU picking через `gl.readPixels`;
- выделение детали;
- кнопку «Снять выделение»;
- `Esc` для снятия выделения;
- полноэкранный режим.

## Windows EXE и release gate

GitHub Actions собирает `B3D-Publisher.exe` как one-file Windows executable. Перед выпуском workflow **не только компилирует EXE**, но и запускает уже собранный EXE на эталонном `.b3d` и проверяет, что он действительно создаёт автономный HTML.

Release-artifacts:

```text
B3D-Publisher.exe
SHA256.txt
```

## Проверка

```bash
python -m unittest discover -s tests -v
```

Дополнительный workflow `B3D container forensics` отдельно проверяет прямой разбор контейнера, все 37 деталей, 36 обработок и итоговую CSG-геометрию эталонной модели.
